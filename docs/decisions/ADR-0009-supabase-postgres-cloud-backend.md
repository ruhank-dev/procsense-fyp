# ADR-0009: A hosted cloud backend on PostgreSQL with Supabase accounts, built early, for a product that will be sold

**Status:** Accepted 13 October 2026 (owner's decision after the supervisor asked for the VR application to connect to a database; planning only, no implementation yet) · **Related:** ADR-0005, ADR-0006, ADR-0008 · **Replaces:** the "optional local SQLite server" decisions of `p1-backend`

## Context
The first backend plan was an optional server on a laptop in the same Wi-Fi network as the headset, with SQLite and a per-device key. That fits a single-site demo. The product is now meant to be sold as software as a service: many organisations, many people using it at the same time, an application login, and one global dashboard across headsets and sites. The supervisor has also asked for the VR application to be connected to a database soon. The `p1-backend` plan named both triggers itself ("concurrent multi-user writes" and "multi-site use" were its revisit conditions).

## Decision
1. **Database: PostgreSQL, hosted by Supabase.** The data is relational (organisations, people, sessions, scores, competencies) and the main product value is reporting across it, which is SQL work. Supabase is plain PostgreSQL plus login, so the team does not write or secure its own account system and can move to any other Postgres host later (a backup restore and a connection string).
2. **Login: Supabase Auth** (email and password for the web dashboard). The headset signs in with the same accounts, first with the ordinary form and then with a device code shown in the headset and approved on a phone or computer, because typing in VR is painful.
3. **The headset and the dashboard never read or write the database directly.** Everything goes through the FastAPI service, which checks who is calling, what organisation and role they have, and what they may see. Row-level security is switched on in the database with no open policies as a second lock, never as the only one.
4. **Organisations and roles from the start**: organisation, membership with a role (trainee, supervisor, organisation admin), cohorts. Adding tenancy later would mean rewriting every table and query. Platform administration is done by the team directly in the database until there is a reason to build a screen for it.
5. **The engine stays on the device and offline-first stays.** A session is played, logged and replayable with no network; finished sessions queue on the device and upload when the service is reachable. Practice can run offline with a remembered login; the rules for assessment mode are in `p1-backend-s10`.
6. **The server verifies every uploaded session** by replaying its log through the same engine (a `verify` command of the command-line simulator, run in the server container) and refusing a score that does not reproduce. A result that was not verified is stored but never counted in a dashboard or an assessment. This is what makes the scores worth selling: a modified headset cannot send a better result.
7. **Free hosting while it is a student project:** Supabase free plan for the database and login, and a free container host (Render's free web service is the first choice) for the FastAPI service and the web dashboard served from it. Both are replaceable. The free plans are for development and demonstrations; moving to paid plans is expected before real customers, and the plan keeps that move small (plain Postgres, Docker, environment variables).
8. **The AI is not dropped and not decided here.** The AI services (language model, speech) stay behind the gateway (`p1-backend-s06`). Where they run for a sold product (GPU hosting cost, a customer-site GPU, or a hosted model service) is a separate decision, recorded as an open question (OQ-07) and a deferred task; until then they run on the team's own machines as in `p1-ai-infrastructure`.
9. **Payments and billing are out of scope for now** (DT-125); organisations and roles are designed so billing can attach to an organisation later.

## Consequences
- The backend moves ahead of the rest of the P1 work: a new milestone (M17) holds the accounts, upload, verification, dashboard and operations steps, built alongside the VR work and before the P0 release if the supervisor needs the connection for the demonstration. `p1-backend-s05` and `s06` (audit log, AI gateway) stay in M10.
- Seven steps are added (`p1-backend-s07` to `s13`) and six existing steps are rewritten for PostgreSQL, accounts and cloud hosting.
- New work that did not exist before: hosting and secrets, accounts and roles, the Quest login, server-side verification, a web dashboard, privacy handling (consent, retention, delete my data) and free-tier operations (backups, keep-alive).
- A privacy and terms review by a person qualified to give it is needed before real customers (DT-127). The patients in every case are synthetic, which keeps patient data out of scope, but trainee accounts are personal data.
- Free plans have limits that the plan treats as real constraints: the Supabase free database is small (about 500 MB), pauses after a week of inactivity and has no automatic backups; a free container host sleeps when idle and wakes slowly. The headset's offline queue already tolerates both; the operations step (s13) adds our own backups and a keep-alive.

## Revisit if
The free plans stop being enough (size, pausing or cold starts hurt a demonstration), a customer needs data kept in a particular country or on their own premises, the number of concurrent sessions needs a larger database, or Supabase Auth cannot do something the product needs (single sign-on for an organisation is the likely first case).
