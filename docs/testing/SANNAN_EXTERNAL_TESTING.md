## 1. How to use this page

1. Find your item in the table in section 2. Each item names the steps it closes, what it needs, the procedure, the pass rule and the evidence to keep.
2. Do the procedure exactly. Do not skip a line because it looks obvious; a skipped line is a missing measurement.
3. Record the outcome in a result file, using this form:

   Result file: `docs/testing/results/<ID>.md (put logs, screenshots and videos in docs/testing/results/<ID>/ beside it)` with the fields: ID; date and time (UTC); who ran it; device, OS version, build id and git commit (or the account, person or machine for a non-device item); result: PASS | FAIL | NOT RUN; numbers measured against the pass rule; evidence file names; notes and anything that surprised you.

   An item is passed only by a result file whose first lines read `Result: PASS` and that names the commit, the device or person and the numbers. Do not tick a step on a verbal report. A result file that says FAIL keeps the step open and is the reproduction recipe: attach the log and say which pass-rule line failed.

   Start the file with the line `Result: PASS`, `Result: FAIL` or `Result: NOT RUN`; this page reads that line to show the status below, and CI fails if the page is not regenerated after a result file is added (`uv run --project tools tools/plans/external_testing.py`).

4. **If it fails:** Write `Result: FAIL`, copy the failing line of the pass rule, attach the log and the exported session, and tell the engineer (Ruhan) the commit. A failing session log replays headless with `task sim -- replay --log <file>`, which is how the engineer reproduces it.
5. **After it passes:** the engineer named in the item sets the step's status with `tools/plans/tick.py` after reading the result file. Nobody ticks a step because a test was reported verbally.
6. **AI simulation is not human testing.** Synthetic data, AI judges and simulated learners are used for development only; the items below that say people are needed are not satisfied by them.

### DC-01

**Frame-time cost with the local model and the recogniser running beside the simulation**

* Who: Sannan
* Why local CI cannot verify it: It needs a headset, a Unity build or a particular machine, which the desktop checks and GitHub Actions do not have.
* Needs: The desktop with the VR scene (Editor play mode or a PC build) and Ollama running; a Quest linked to the PC if the scene is streamed
* Closes steps: [p1-ai-infrastructure-s02](../plans/p1/p1-ai-infrastructure/steps/✅%20p1-ai-infrastructure-s02-dual-gpu-benchmark.md), [p1-ai-language-s02](../plans/p1/p1-ai-language/steps/✅%20p1-ai-language-s02-llm-serving-benchmark.md)
* Features: E57, E69 (plans in `docs/plans/features/<ID>.md`)
* Prepared (already in the repository):
  * `tools/ai/benchmark.py`
  * `docs/research/model_benchmarks.md`

Procedure:

1. Start the VR scene with no model loaded; record 2 minutes of frame time (Unity Profiler or OVR Metrics: average and 99th percentile frame ms).
2. In a terminal run: ollama run qwen3.5:4b-q4_K_M "hello" so the 4B model is loaded, then repeat the 2-minute recording while `uv run --project tools tools/ai/benchmark.py b0 --model qwen3.5:4b-q4_K_M --runs 20` runs.
3. Repeat with the speech recogniser busy (the voice client sending a clip every 10 seconds).
4. Write the three pairs of frame-time numbers and the BT0 line of the benchmark in the result file.

**Pass rule:** Average frame time stays within the headset's refresh budget (13.9 ms at 72 Hz) in all three runs, and the 99th percentile does not exceed 1.5 times the budget. If it does not, write which run failed; the model then runs on the laptop (ADR-0010).

**Evidence to collect:** The result file; the Unity Profiler or OVR Metrics export; the exported session log (`.jsonl`) for any playthrough; a screenshot or short video of the failing moment; the build id and `git rev-parse HEAD`.
