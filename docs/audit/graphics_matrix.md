## Clinical text on Quest 2: composition layers investigated, sharp-text alternative (14 Nov 2026 UTC)

Owner order: compositor layers for the EMR tablet, monitor and menu panel under the 0.8-0.9 eye buffer, or the best supported alternative.

**Availability.** `com.unity.xr.compositionlayers` is not in `unity/Packages/manifest.json` and not in `Library/PackageCache`, but Unity 6000.5.10f1 ships it offline: `Editor/Data/Resources/PackageManager/Editor/com.unity.xr.compositionlayers-2.5.0.tgz` (needs Unity 2022.3+, input system 1.6.3, XR management 4.0.1, XR core utils 2.2.2; all already resolved in this project). OpenXR 1.18 contains `OpenXRCompositionLayersFeature` and quad/cylinder layer handlers compiled only when that package is present (`XR_COMPOSITION_LAYERS` version define). So adding it would not need a download.

**Why not now.** From the package's own documentation (`Documentation~/composition-layer-interactive-UI.md`, `layer-transparency.md`, `known-issues.md`):
1. Interactive UI on a layer is drawn by a hidden camera into a render texture and mirrored onto the quad (one extra camera and render target per panel, one user layer each). That contradicts the "one XR camera" row above and adds passes on the tile GPU; the monitor and EMR change every frame.
2. A layer with order > 0 is drawn over the whole eye buffer: the controller ray, hands and staff walking in front of the monitor would be hidden behind it. The documented fix is a Projection Eye Rig, whose projection layer "does not support Single Pass Instanced" (two more stereo renders). Underlays (order < 0) need the camera cleared to alpha 0 and a hole in the scene; the Editor emulation "can produce different results than the hardware compositor; always verify on device".
3. Pointer input goes through a mirrored collider, not our `WorldUiRaycaster`/`GraphicRaycaster` path that the menu, EMR and monitor buttons use today.
4. None of the above can be checked without the headset, and the owner's rule is to keep the app buildable and not risk pointer interaction or stereo.

**Implemented instead** (all layout-neutral; `Scripts/UI/Accessibility/ClinicalText.cs`):
- Every label on the clinical canvases (`Tablet`, `EMR shell`, `EMR`, `Monitor`, `Game flow`, `Main menu`) uses one shared copy of the font's Mobile SDF material with face dilation 0.1, so 1-2 px strokes keep their contrast when the eye buffer is resampled. One material per font: batching and glyph metrics unchanged; other panels keep the font material. The font itself stays LiberationSans SDF (static 1024 atlas, 86 pt sampling, padding 9, bilinear, no mips: already the right SDF setup).
- `QuestPerformanceProfile.Controller.Step` takes a floor: while a clinical panel is enabled, within 2 m and 30 degrees of the view direction, dynamic resolution does not go below 0.8 (the profile's start scale) and a lower scale is raised at once; elsewhere it may still go to 0.7. Cost: at most the 0.8 baseline GPU load while reading.
- The menu panel is read from 1.5 m (`MenuFlowInstaller.Distance`), not the 1 m default, so its text floor (24 headset pixels at the Quest 3 reference, `Readability`) follows the real distance (its 20 pt status lines rise to 21 pt).
- `Readability.Quest2EyeBufferPixels` reports each panel's smallest label in estimated eye-buffer pixels at 0.7/0.8/0.9 (estimate: 1440 px per eye at 1.0, assumed 90 degree FOV). Not a legibility claim.

Not changed: panel scale and positions (the tablet and monitor canvases sit on meshes), font sizes beyond the existing floor (larger sizes would truncate clinical text with an ellipsis), contrast (already WCAG checked by `AccessibilityTests`), panel distance (moving the menu closer widens it into the foveated periphery).

Tests: EditMode `ClinicalTextFloorTests` (floor, raise, range, reading cone, PPD maths), PlayMode `ClinicalTextTests` (shared material on clinical panels only, menu distance, reading cone on a built panel, size report) plus the existing `AccessibilityTests`; change-aware check `unity_playmode_clinical_text`. **Legibility on the device stays NOT TESTED (headset DC-13).**

## Sharpness regression after the GPU overhaul (15 Nov 2026 UTC)

Owner report: real Quest 2 footage after the overhaul looks grainy, blurry, pixelated and jagged (FPS better). No headset, Editor capture or measurement was used for this section: every number below is arithmetic from the project files, and FPS / GPU ms are **not claimed**.

**Effective eye-buffer pixels** (Quest 2 panel 1832 x 1920 per eye = 3.52 Mpx; the runtime's recommended eye buffer at scale 1.0 is 1440 x 1584 = 2.28 Mpx per the existing code comments, to be confirmed by the device log):

| Configuration | Allocated | Viewport | Drawn per eye | Share of panel pixels | AA / FFR |
|--|--|--|--|--|--|
| Pre-overhaul baseline (7b446e28) | 1.0 = 1440 x 1584 | 1.0 | 1440 x 1584 | 65% | MSAA 4x, FFR off |
| First overhaul (a35d6fa3), release APK | 0.9 = 1296 x 1426 | 0.889 | 1152 x 1267, **held there** (no GPU time, see below) | 41% | MSAA off, FFR High |
| First overhaul, dynamic range | 0.9 | 0.778-1.0 | 1008 x 1109 to 1296 x 1426 | 32-53% | as above |
| Sharpness revision (this change) | 1.0 = 1440 x 1584 | 0.9 start (0.85-1.0) | 1296 x 1426 start; 1224 x 1346 min; 1440 x 1584 max | 53% (47-65%) | MSAA off (2x selectable in diag), FFR Medium |

The two scales stack by design (eye-texture scale x viewport scale = effective scale; URP `renderScale` stays 1.0). No second, unintended reduction was found: nothing else in production writes `eyeTextureResolutionScale`, `renderViewportScale` or the URP scale. If the Vulkan path ignores the viewport scale, the first overhaul drew 1296 x 1426 and the revision draws 1440 x 1584.

**Root causes (source evidence).**
1. Resolution: the first overhaul drew 64% of the baseline's pixels (0.8 linear), on top of losing 4x MSAA. 0.8 of the runtime size is 63% of the panel width, so each eye-buffer pixel is magnified about 1.6x by the compositor: soft image, stair-stepped edges.
2. The scale could never rise in the release APK: `PlayerSettings.enableFrameTimingStats` is 0 in the project and `BuildScript` turned it on for the diagnostic APK only, so `FrameTimingManager` returned no GPU time and the driver held 0.8 for the whole session. In the diagnostic APK `PerfToggles` re-applied the start scale every 0.5 s, which pinned it too.
3. Fixed foveation High with Subsampled Layout lowers the shading rate in the periphery the most; the edges of the footage are where blockiness shows first.
4. No anti-aliasing at all (MSAA 1, no post AA by design): geometric edges, thin cables and alpha-clipped hair/eyelashes alias and shimmer as the head moves ("grain"); alpha-to-coverage needs MSAA.
5. Close-up textures: the patient's skin was ASTC 6x6 with anisotropy 1, the patient clothes had no Android override, the mattress cover was halved to 1024 and its normal map to 512 by the overhaul's texture budget, and character normal maps were ASTC 6x6 (block artefacts in normal maps read as speckle under lighting).
6. Not a sharpness cause but found here: `XrPerformanceSettingsFeature Android` was `m_enabled: 0` in every commit (7b446e28, a35d6fa3, 98da6c71, 3096dbdd) although the verifier passed on the working tree on 14 Nov; the SustainedHigh CPU/GPU hint has therefore never been in a built APK. Enabled again; re-check after any Editor session that saves the OpenXR settings.
7. Other overhaul simplifications checked and left alone: 52 environment/prop materials moved to Simple Lit and 179 materials have environment reflections off (flatter, not blurrier; none of them is the patient, gown or bed); LOD cross-fade dithering is off in the Android URP asset (no dither grain); `lodBias 0.7` predates the overhaul; mipmaps are on for every 3D texture; PatientBay floor textures keep 8x anisotropy. Symmetric Projection widens the projected frustum slightly, which may lower pixel density a little at the same buffer size: unmeasured, kept.

**Changes (old -> new).** `QuestPerformanceProfile`: eye buffer 0.9 -> 1.0, start 0.8 -> 0.9, min 0.7 -> 0.85, max 0.9 -> 1.0, foveation 1.0 (High) -> 0.5 (Medium), Subsampled Layout kept; `QuestRenderTier` defaults and `ClinicalText.FloorScale` (0.8 -> 0.9) now come from the profile constants (single source); `BuildScript`: Frame Timing Stats on for release and diagnostic APKs, committed value restored after the build; `PerfToggles`: scale applied once per preset (was every 0.5 s); close-up textures as in the ASTC row; XR Performance Settings re-enabled. Kept: baked lighting, no realtime shadows, culling, ASTC everywhere, LODs, Vulkan/OpenXR, multiview, FFR, MSAA 1 default.

**Sharpening: not added.** URP's only sharpening (FSR/RCAS) runs in a final full-screen post pass, which needs an intermediate texture and costs a full-screen read and write per eye on the tile GPU, and it would break the "no fullscreen copies" row; the gain over simply drawing more pixels (0.9-1.0) is small. Meta's compositor-side sharpening is not exposed by the Unity OpenXR plug-in used here.

**Diagnostic build controls** (left thumbstick click cycles; the sharpness set is the first six clicks after B0): B90 FFR High, B91 MSAA 2x, B92 MSAA 2x + FFR High, B93 fixed 1.0, B94 fixed 0.85, B95 the first overhaul profile (0.9 buffer, 0.8 start, 0.7-0.9, High). **Recording versus real degradation (cannot be separated here).** The owner's evidence is headset footage. ## Sun shaft regression after the GPU overhaul (15 Nov 2026 UTC, DT-311)

Owner report: on the Quest 2 the dust motes are visible but the window sun shafts have disappeared.

**Checked and not the cause.** Hosts `Door sun shafts` (bay, corridor) and `Sun shafts` are active and `DesktopOnly.ShowOnAndroid` defaults to true (only the diag `ShaftsOff` preset hides them); RoomVisibility never culls the camera's own room and the PlayMode check shows no `forceRenderingOff` with the Android culling on; the shader, both materials and the noise texture are packed in the last Android build report (`Library/LastBuild.buildreport`, `sharedassets2/4`); the shader carries instancing and eye-index macros and uses no depth texture; the shafts are additive unlit geometry, so baking the lights and disabling the soft clinical key did not affect them; beams start on the window glass and follow the baked sun (`_ShaftDir` equals `Sun through window` / `Corridor sun`).

**Root cause.** `BakeEverything.Apply` moved the shaft materials from `ProcSense/Sun Shaft` to `ProcSense/Sun Shaft Baked`, which (1) culled back faces: each prism lost its far wall and drew nothing at all when the eye stood inside a beam (the usual bay position), and (2) sampled `.r` of `sunshaft_noise.png`, which was imported as Single Channel **Alpha** (`singleChannelComponent: 0`), so the density term collapsed to about 0.2. Together about a quarter of the original light.
