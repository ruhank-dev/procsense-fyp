## 3. Verification methods

- **Walkthrough and flat text files:** the Markdown was converted *back* to the original line sequence and compared with the source, line by line (exact equality), plus a word/symbol census with no classification step.
- **CSV files:** each Markdown table was parsed back and compared cell by cell with the CSV (rows, columns, order). A real Markdown parser then confirmed every table renders with the same row and cell counts (no truncation).
- **JSON files:** the fenced block equals the file text exactly and parses to the identical structure.
- **Master Plan / Implementation Guide TXT:** every non-blank content line is present in the same order (headings or fenced lines), plus a word/symbol census.
- **Master Plan / Implementation Guide PDF:** the Markdown was written from the structured document that produced the PDF. It was checked against the PDF text in two steps: (1) a letter-and-digit census (every letter and digit, case-insensitive) against the same document re-rendered once without repeated table headers — equal to the character; (2) the delivered PDF versus that re-render, line by line — the only differences are repeated table headers on continuation pages, the cover and page footers.

## 5. Conversion limitations (information that cannot be represented perfectly)

1. **Walkthrough tables.** The source file is plain text in which each table was already flattened by whoever produced it: the cells of a row appear on one line separated only by single spaces, with no cell delimiters. Rebuilding `|` tables would mean guessing where one cell ends and the next starts, which could change the medical meaning. So every table row is kept exactly as the source line, in order, rather than converted into a pipe table. No cell, number or word is lost; only the column borders were never in the file. (CSV files and the Master Plan/Guide PDFs, which do have real cell structure, *are* converted into true Markdown tables.)
2. **The walkthrough has no pictures.** The file named `.pdf` is UTF-8 text (12,599 lines, about 225 pages). There are no figures or drawings in it, so none exist to convert. Its page boundaries are kept as a horizontal rule followed by the two-line running header, which includes the page number.
3. **Escaping.** Markdown treats characters like `_ * ~ [ ] < >` specially, so in the raw `.md` text some appear with a backslash (for example `\_`). They display normally when rendered, and the exact-reversal check strips these backslashes to get back the original characters.
4. **Line breaks.** Walkthrough lines are hard-wrapped in the source and every line break is kept (two spaces at the end of each line). `•` at the start of a line became a Markdown list item `- `; a `•` in the middle of a line is unchanged.
5. **Page furniture of the two PDFs** is not reproduced because Markdown has no pages: footer text (document name and page numbers), the section kicker repeated above every section, and table header rows repeated on continuation pages. The cover, contents and all section content are included. The PDF's colours, fonts and layout cannot be represented.
6. **PDF versus TXT of the same document are different renderings.** The TXT carries three metadata lines (version, team, status) at its top that the PDF cover does not show, and the TXT shows tables in text form. Both are converted separately and completely.
7. **CSV details.** A line break inside a cell is written as `<br>` (20 cells, all in `stacked_cases_compact.md`); `|` inside a cell is written `\|`; the invisible UTF-8 byte-order mark at the start of the CSV files is not carried. No cell had leading/trailing spaces.
8. **Whitespace.** Windows (CRLF) and Unix (LF) line endings are normalised; trailing spaces were not present in the sources.
9. **Source content left as found.** Inconsistencies in the walkthrough (for example duplicate patient IDs, a symptom duration given as both 14 h and 20 h, one NICE versus CG174 bolus volume) are listed in `ProcSense_Change_Report.md` and are **not** altered in the Markdown copy.
