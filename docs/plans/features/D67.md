## 1. Intended user experience

The system keeps an honest picture of each trainee: what they have shown they can do, what they have repeatedly struggled with, and how sure it is; a single slip does not label them weak.

## 2. What exists and what is missing

**Exists in the repository:**

- Elo ratings per behaviour
- pseudonymised history
- evidence store with confidence

**Missing:**

- session evidence schema
- Bayesian learner model
- error pattern status
- LLM performance interpreter
- post-session update job

**Deterministic foundation:** Evidence schema, update rules and evidence weighting; AI interpretations are stored as hypotheses with confidence, never as ground truth.

## 3. The AI in this feature (seven questions)

| Question | Answer |
|---|---|
| 1. What is the AI supposed to do? | Interpret structured performance summaries to suggest likely misconceptions and learning needs. |
| 2. Why is AI useful here? | Counts tell what happened; an interpreter can relate errors across competencies (e.g. late allergy check plus missed old note suggests poor record review) and propose targeted practice. |
| 3. Which method for which part? | Bayesian mastery model (Beta-binomial per competency, optionally Bayesian knowledge tracing) decides mastery with uncertainty; pattern detection (D40) marks demonstrated weaknesses; LLM interpreter proposes hypotheses. |
| 4. Deterministic parts still needed | Evidence schema, posterior updates, thresholds for 'demonstrated' (at least 3 sessions and posterior mean under 0.5 with interval width under 0.3), pseudonymity. |
| 5a. AI already implemented | None. |
| 5b. AI missing | Learner model, update job, interpreter. |
| 6. What we must build | p1-personalisation s01, s02, s04. |
| 7. How we prove it beats a simple baseline | Predictive log-loss of next-session performance versus Elo; interpreter hypotheses confirmed by later evidence more often than chance. |

### D67.c3 — LLM performance interpreter

| Field | Value |
|---|---|
| Kind | AI (LLM) |
| Status | Implemented and tested |
| Purpose | Hypotheses about needs. |
| Architecture and model or algorithm | Qwen3.5 4B reads the profile summary; returns hypotheses with cited evidence ids and confidence. |
| Models | MC-04 |
| Data | — |
| Input schema | `ProfileSummary (no free text from the trainee)` |
| Output schema | `Hypotheses[{need, competencies[], evidence_ids[], confidence}]` |
| Processing flow | summarise → prompt → check every evidence id exists → store as hypothesis |
| Validation of outputs | Evidence ids exist; stored as hypotheses only. |
| Errors | Timeout or server error: one retry, then no hypotheses (pattern detection only); logged with prompt version and model digest. |
| Hallucinations | Output must match a JSON schema whose enums are approved ids; the grounding validator rejects invented drugs, values, diagnoses, events and hidden facts. |
| Inconsistent results | Output is cross-checked against the structured case or facts it was given; any mismatch rejects it. |
| Model unavailable | Feature switch reports off; no hypotheses (pattern detection only). The session never waits on the model. |
| Invalid input | Inputs are schema-validated before the model is called; invalid input is a 4xx with field errors. |
| Tests | hypothesis confirmation rate |
| Metrics | later confirmation rate |
| Baseline comparison | Pattern detection only. |
| Acceptance | Hypotheses confirmed by later evidence at a higher rate than random competency picks. |
| GTX 1660 SUPER (desktop) | Runs as a batch job on the desktop; larger models (8B with offload) acceptable because time is not critical. |
| RTX 4050 Laptop | Batch job when Unity is not running. |
| Memory | CPU offload uses system RAM; keep batch size small on 16 GB. |
| Latency | Offline; minutes per batch acceptable. |
| Deployment | Offline CLI on either machine; results stored and versioned; optional remote GPU for large batches. |
