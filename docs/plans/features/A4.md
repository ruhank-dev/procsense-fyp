## 1. Intended user experience

Some cases have two or three problems at once (an infection and an allergy, a diabetic patient who is also nil by mouth) and the trainee must prioritise.

## 2. What exists and what is missing

**Exists in the repository:**

- hand-made stacked cases (STK-*)
- problem types and priority ladder P1 to P4

**Missing:**

- stack templates for the solver
- AI composition of stacked plans

**Deterministic foundation:** Priority ladder and Stage B decide whether a stack is coherent.

## 3. The AI in this feature (seven questions)

| Question | Answer |
|---|---|
| 1. What is the AI supposed to do? | Choose which problems interact meaningfully and describe how they interact. |
| 2. Why is AI useful here? | Interaction effects (allergy constrains antibiotic choice in sepsis) are knowledge-heavy; the KB plus an LLM can propose interacting stacks rather than unrelated ones. |
| 3. Which method for which part? | LLM proposes stacks with interaction rationale; KB relations and ladder rules check them. |
| 4. Deterministic parts still needed | Ladder rules, Stage B. |
| 5a. AI already implemented | None. |
| 5b. AI missing | Stack proposals with interaction rationale. |
| 6. What we must build | Stack slots in the plan schema; interaction relations in the KB. |
| 7. How we prove it beats a simple baseline | Raters judge interaction quality: AI stacks versus random valid stacks. |

### A4.c2 — Interacting-problem proposals

| Field | Value |
|---|---|
| Kind | AI (LLM + retrieval) |
| Status | Blocked |
| Purpose | Stacks whose problems interact. |
| Architecture and model or algorithm | Part of the plan composer (A2.c2) with an interaction field. |
| Models | MC-01 |
| Data | ST-KB |
| Input schema | `Objectives + KB interaction relations` |
| Output schema | `ScenarioPlan.secondary_problems with interaction_rationale` |
| Processing flow | retrieve interaction relations → propose → verify each interaction exists in KB |
| Validation of outputs | Every claimed interaction is a KB relation. |
| Errors | Timeout or server error: one retry, then random valid stack; logged with prompt version and model digest. |
| Hallucinations | Output must match a JSON schema whose enums are approved ids; the grounding validator rejects invented drugs, values, diagnoses, events and hidden facts. |

| Model unavailable | Feature switch reports off; random valid stack. The session never waits on the model. |
| Invalid input | Inputs are schema-validated before the model is called; invalid input is a 4xx with field errors. |
| Tests | interaction-claim check; rater study |
| Metrics | share of stacks with a real interaction |
| Baseline comparison | Random valid stack. |
| Acceptance | At least 80 percent of AI stacks contain a KB-confirmed interaction versus baseline rate. |
| GTX 1660 SUPER (desktop) | Desktop GTX 1660 SUPER (Turing, 6 GB, no tensor cores), measured 16 Oct 2026 with the machine idle: qwen3.5:4b-q4_K_M (3.3 GB weights, thinking off) sits 100 percent on the GPU (3.1 GB at a 4k context) and generates about 59 tokens per second, a 50-token patient reply taking about 1.0 s (p95 1.15 s); qwen3.5:9b-q4_K_M (6.6 GB) does not fit and runs 57 percent on the GPU with the rest on the CPU, about 12 tokens per second and about 5 s for the same reply, so it is the offline batch model only.
