# p3-03-scenario-selection-generation — Random, clinically valid scenarios for both modes (SCN)

Status: Planned (P3, 7 November 2026). Nothing in this plan is implemented. Needs owner decision D1 (roadmap section 6).

## 1. Objective and final user-facing behaviour

Every session can be a different, medically coherent patient. Training draws from the approved training pool and, when the server is reachable, from freshly generated practice cases. The examination draws from the examination pool. The player can retry exactly the same scenario (same case and seed) or ask for a new one. No session ever shows contradictory patient information, a draft case or a case whose approval level does not allow the mode.

## 5. Architecture and integrations

```
SessionRequest(mode, procedure, level, source?, seed?)            (P3-SES-06)
   │
   ├─ source = generated (training only, server reachable) ─► /scenario-packages/next ─► sealed package ─► engine replay check ─► session
   │                                                           └─ failure / offline ─► authored pool (message shown)
   └─ source = authored ─► ScenarioPicker(catalogue, mode, procedure, level, seed, recent ids) ─► caseId
                                                                   │
                                          ContentMode.Load(mode, checkManifest) ─► excluded? → pick next, log reason
                                                                   ▼
                                   session (seed recorded) + briefing facts + avatar profile (P3-AST-03)
```

- **Randomness is deterministic:** the picker uses `SimRandom(seed)`; the seed is shown on the results screen and saved in the header, so a scenario can be replayed or reported.
- **Variation inside valid limits:** variation comes only from approved case files, approved adversarial blocks and the engine's seeded events. Nothing is randomised outside the content that passed validation.
- **Examination pool (D1):** options in the roadmap. The picker reads the allowed statuses from `ContentGate`, so the decision changes data, not code.

## 7. Dependencies and execution order

P3-SCN-02 → P3-SCN-03 → (04, 05, 09, 10) → 07 after D1 → 08 after the avatar swap → 06 after the flow → 11.

## 8. Frontend components

Procedure card case counts (P3-MNU-04), briefing card (P3-MNU-07), seed and source line on results (P3-RES-04).

## 9. Backend and API changes

None required; `/scenario-packages/next` already exists. Optional: add `procedure` and `level` to its request schema if not present (checked in P3-API-02).

## 10. AI and voice integration

Generated cases use the cloud narrative and critic only on the server, before the session; the headset receives a sealed, deterministic package. The examination never uses generated content unless D1 explicitly allows it.

## 11. Unity objects, prefabs, animations and assets

Patient avatar profiles (P3-AST-02/03); bay variant for the emergency department setting (P3-AST-08).

## 12. Performance

The catalogue is a small JSON loaded once; the picker runs in microseconds; content load is the existing cost.

## 13. Error handling and edge cases

Empty pool; manifest mismatch on device (content refused: return to menu with the message); generated package refused by the engine; same case drawn twice in a row; seed overflow; a case whose patient profile is missing.

## 14. Testing

Core xUnit for the picker and briefing; tool tests for the catalogue; PlayMode for generated/offline fallback; golden replay for retry.

## 15. Acceptance criteria

1. Ten new training sessions of S1 give at least five different cases.
2. The examination plays only cases allowed by D1, never a draft or training-only case.
3. Retry gives the identical case and event timing.

## 16. Definition of Done

All SCN tasks Done; decision recorded; `docs/context` and the Change Report updated; CI green.
