# p1-backend-s09 — Server-side session verification by replay

Milestone: **M17 Cloud platform — Supabase database, accounts, sync and dashboard**

## What
Every uploaded session is replayed on the server through the same engine that produced it, and counts only if the replay reproduces the log. Two parts: a `verify` command in the command-line simulator (and a version-2 session file header), and a verification worker in the server that runs it for pending sessions and stores the result, the report and the scores.

## Why
The product sells results. If the headset is trusted, a modified application can send any score it likes. The engine is deterministic and every action is logged, so the server can re-run the session and check the hash, which no spreadsheet-style product can do. It also tells the dashboard exactly which content and engine version a result belongs to.

## How to implement
1. Session file header v2 (engine side, `src/ProcSense.Core/Replay/SessionFile.cs`): add the session id (given by the host), the content version (from the manifest), the engine version and `scenario_package_hash` (empty for the fixed cases, the SHA-256 of the generated scenario package otherwise). They are outside the replay hash, so existing golden runs and hashes do not change; replay still reads version 1 files.
2. `procsense-sim verify --log <file> --content <dir> [--json out.json]`: loads the content, checks it against the manifest, replays, and prints a JSON result `{ok, reason, case, mode, content_version, engine_version, log_hash, end_state, result, process_score}` and writes the report page and facts JSON. Exit code 0 only if everything reproduces. The reasons are fixed codes: `HASH_MISMATCH`, `CONTENT_VERSION_UNKNOWN`, `ENGINE_VERSION_UNSUPPORTED`, `CASE_NOT_ALLOWED_FOR_MODE`, `LOG_MALFORMED`, `PACKAGE_MISSING`, `PACKAGE_LOADER_MISSING`.
3. Mode check: a session uploaded as assessment counts as assessment only if its case was approved for assessment in that content version (`ContentMode`, `p0-case-library-s01`); otherwise it is stored as practice and says why.
4. Server container: the published self-contained Linux binary of the simulator and the content packages of the supported content versions are in the image; the supported versions are a setting. A log made with an older engine or content version is `unverifiable`, stored, kept out of every total and shown to its owner with the reason, never silently dropped.
5. Worker: pending sessions are verified one at a time with a timeout and memory limit. The queue is the `status` column, not memory, because the free host sleeps and restarts; a sweeper runs when the service wakes and from a scheduled call (`p1-backend-s13`). A verified session gets its score rows, behaviour rows, report page and facts JSON filled in one transaction.
6. Generated scenarios: `verify` takes an optional `--package <file>`, and the worker fetches the package named in the header from `scenario_package` (`p1-backend-s02`) and checks its hash before replaying. Loading a package into the engine is the loader extension of `p1-live-scenario-generation-s10`; until it exists, a session with a package hash is stored as `unverifiable` with the reason `PACKAGE_LOADER_MISSING` and kept out of totals (DT-134). A generated scenario is practice only: a log that claims assessment mode with a package hash is rejected with `CASE_NOT_ALLOWED_FOR_MODE`.
7. A rejected session keeps the reason and the hash and is visible to the platform administrator; repeated rejections from one user are counted.

## Verification
EXP-BE-5: change one score, one action and the content version in a log → all three refused with the right reason. A correct log from the headset, from the command line and from a golden run verifies and gives the same report as the command-line `report`. The verifier is time-limited and cannot be made to read a file outside its temporary folder. Golden runs and hashes are unchanged by the header change.

p1-backend-s02; p0-scoring-debrief-s05; p0-case-library-s01.

## Common issues
Replaying costs time and memory on a small free host → one at a time, a queue in the database, a sweeper after a wake-up. An engine change makes old logs unverifiable → keep supported versions in a setting and record which engine version each result came from. Never pass an uploaded file name to a command line → write it to a temporary file with a generated name.

## Implementation notes (13 Oct 2026)
- **Two halves, in two places.** The engine half is a small change to Ruhan's code on its own branch (`myt1x54/engine-verify-header-v2`, from main, 7 files, about 390 lines added and 3 changed, golden runs unchanged) for him to review: `SessionFile.Write` takes an optional `SessionMeta` and then writes the version 2 header (session id, content version, engine version, scenario package hash, all outside the log hash), `SessionFile.HeaderOf` reads a header, `SessionVerifier` (Core) does the verifying and `procsense-sim verify` prints its verdict as one line of JSON (exit 0 only when verified); `run` now writes the version 2 header (`--session-id`, `--package-hash` optional). The server half is on the backend branches.
- **What `verify` checks, in order:** the header; the engine version; a named package (needs the bytes and the matching hash, and until the generation loader exists the answer is `PACKAGE_LOADER_MISSING`, DT-134); the content version against the content's manifest; the content files against the manifest; that the log text really has the hash in its header; that the case exists and is allowed for the mode (`CASE_NOT_ALLOWED_FOR_MODE`: a training-only case is never an assessment); then it replays the actions with the header's options (level, variant, noise) and requires the replay to produce the header's hash (`HASH_MISMATCH`), and builds the debrief facts with Ruhan's scorer. The reasons: `LOG_MALFORMED`, `CASE_UNKNOWN`, `ENGINE_VERSION_UNSUPPORTED`, `CONTENT_VERSION_MISMATCH`, `CONTENT_HASH_MISMATCH`, `CASE_NOT_ALLOWED_FOR_MODE`, `PACKAGE_MISSING`, `PACKAGE_LOADER_MISSING`, `HASH_MISMATCH`.
- **What it proves and what it cannot:** the score follows from the recorded actions under these rules, and a changed effect or action is refused (the replay must reproduce the log; a changed log with a recomputed hash still fails because the replay produces the original). It cannot prove a person made the actions.
- **The server worker** (`server/verification/`): the queue is the `status` column; a session is claimed with `FOR UPDATE SKIP LOCKED`; the engine is run on a file with a name the service chose, with a time limit, a CPU limit on Linux, an output cap and an environment with every secret removed. Verified: the result, the end state, the score rows, the behaviour rows, the facts JSON and the HTML report are stored. A refusal that means "this service cannot judge it" is `unverifiable`; one that means "this session is wrong" is `rejected`. No verdict (crash, timeout, unreadable output) leaves it pending and counts an attempt; after 3 it is `unverifiable` with `VERIFIER_ERROR`. A content version the service does not hold, or an engine version outside `SUPPORTED_ENGINE_VERSIONS`, is `unverifiable` without running the engine. Triggers: a background task after each upload, a sweep when the service starts, and `POST /internal/verify-pending` (closed unless `INTERNAL_KEY` is set).
- **Content for verification:** a headset plays with a package of one mode and writes its version; the service holds a folder per version for practice and for assessment (`tools/content/package_versions.py`, `task server-engine-prepare`, outside git) and the Linux engine; the Dockerfile copies them; CI builds them before the image and checks that the engine inside the image runs a session and verifies it.
- **Found while building:** Ruhan's engine writes extra header fields when they are not the default (`level`, `variant`, `noise`); the server's strict header would have refused such a session, so they are accepted now. The upload route stores the header line exactly as it arrived because the log alone cannot be replayed without it (migration `0004`).
- **Decisions to confirm:** a session claiming assessment on a case that is not approved for assessment is rejected (not stored as practice); the engine version string is `CoreInfo.Version`, which nobody bumps yet, so for now any behaviour change shows as a `HASH_MISMATCH` rather than as `ENGINE_VERSION_UNSUPPORTED` (DT-140).
- **Tests:** engine side 13 (`SessionVerifierTests`); server side 31 new (stand-in engine and the real one), tools 2 new; the image and the engine inside it are checked by the CI job (not run on this laptop: the Linux engine and image build need downloads that are too slow here, DT-141).
